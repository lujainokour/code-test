# دليل دراسة ومناقشة قاعدة CodeMentor AI — المرحلة الثالثة

التنفيذ الحالي قاعدة SQL Server مستقلة تضم **23 جدولًا و169 عمودًا**. نُفذت 102 فحوص SQL فعلية بنجاح دون إخفاق في آخر تشغيل مسجل. لا يعني ذلك أن واجهة المشروع اتصلت بالقاعدة: الواجهة الحالية بقيت كما هي، محلية في المتصفح، والمرشد ردوده مجهزة مسبقًا والتوصيات قواعد ثابتة. سجلات المتعلمين في SQL أمثلة أكاديمية خيالية وليست قياسات حقيقية.

## كيف نقرأ التصميم؟

PK يحدد الصف، وFK يربطه بصف أب موجود. المفتاح المركب يجمع أكثر من عمود عندما تكون الحقيقة هي اجتماع القيم. IDENTITY يولد أرقامًا بديلة لكنه ليس لكل مفتاح، ولا يعد صفوف الجدول، وقد يترك فجوات حتى بعد ROLLBACK. UQ يفرض تفرد مفتاح مرشح آخر. CHECK يحدد قيم الصف المسموحة، وDEFAULT يقترح قيمة عند عدم إرسالها، وNOT NULL يمنع غيابها. CHECK في SQL Server يقبل UNKNOWN؛ لذلك شروط الحقول الشرطية تتضمن IS NOT NULL صراحة عند الحاجة.

الأزمنة من نوع datetime2(3) وباتفاق UTC. SYSUTCDATETIME يعطي وقت الخادم الجديد؛ لا نستنتج زمن إكمال قديم من زمن استيراده. النصوص البشرية NVARCHAR لدعم العربية. المخطط لا يحقق وحده المصادقة أو الإذن أو أمان تشغيل Python.

## موضوعات SQL بالأمثلة

كل الأمثلة قابلة للتنفيذ في [academic-examples.sql](academic-examples.sql)، والفحوص السلبية في [verification.sql](verification.sql). استخدم قاعدة الاختبار الجديدة فقط.

### SELECT وWHERE

~~~sql
SELECT CourseId, Title FROM dbo.Courses WHERE PublicationStatus='Published';
~~~

SELECT يختار أعمدة، وWHERE يستبعد الصفوف قبل التجميع. INSERT يضيف كورس Draft، وUPDATE يغير عنوانه، وDELETE يحذفه ما دام غير مرتبط بأدلة. المثال التنفيذي يضع هذه العمليات داخل معاملة تنتهي ROLLBACK؛ لا نحذف إنجازات أو نعيد إنشاء القاعدة.

### أنواع JOIN الأربعة

~~~sql
SELECT u.FullName,e.EnrollmentId
FROM dbo.Users u INNER JOIN dbo.Enrollments e ON e.StudentId=u.UserId;
SELECT u.FullName,e.EnrollmentId
FROM dbo.Users u LEFT JOIN dbo.Enrollments e ON e.StudentId=u.UserId;
SELECT l.Name,c.Title
FROM dbo.Courses c RIGHT JOIN dbo.Languages l ON l.LanguageId=c.LanguageId;
~~~

INNER يعرض المتطابق فقط. LEFT يحتفظ بكل صف يسارًا، لذلك يظهر حساب الأدمن مع EnrollmentId=NULL. RIGHT يحتفظ بكل لغة يمينًا ولو لم يوجد كورس. FULL يحتفظ بغير المتطابق من الجهتين؛ المثال الأكاديمي يقارن عدد المهتمين بكل لغة مع عدد الكورسات في تجميعين مستقلين. وجود FK لا يلغي فائدة FULL عندما نقارن إسقاطات مستقلة.

### GROUP BY وHAVING والدوال التجميعية

~~~sql
SELECT AssessmentId,COUNT(*) Attempts,AVG(ScorePercent) MeanScore,
       MIN(ScorePercent) Lowest,MAX(ScorePercent) Highest,SUM(CorrectCount) CorrectAnswers
FROM dbo.vAssessmentScores WHERE Status='Submitted'
GROUP BY AssessmentId HAVING COUNT(*)>=1;
~~~

GROUP BY يجمع محاولات الاختبار نفسه. COUNT يعد الصفوف، SUM يجمع الإجابات الصحيحة، AVG المتوسط، MIN وMAX الحدود. WHERE يرشح المحاولات قبل التجميع؛ HAVING يرشح المجموعة بعد حساب COUNT. AVG يتجاهل NULL، لذلك نميز النتيجة المجهولة عن الصفر.

### Subquery

~~~sql
SELECT l.Title FROM dbo.Lessons l
WHERE EXISTS (SELECT 1 FROM dbo.LessonCompletions c WHERE c.LessonId=l.LessonId);
~~~

هذا استعلام فرعي مرتبط؛ يتحقق من وجود إكمال للدرس الحالي دون تكرار الدرس لكل طالب أكمله. يمكن أيضًا مقارنة درجة بمحسوب فرعي مثل متوسط الدرجات.

### Indexes

لكل جدول PK عنقودي Clustered؛ الجداول تُنظم منطقيًا بحسب هذا المفتاح، دون وعد بترتيب SELECT بلا ORDER BY. الفهرس Nonclustered مسار بحث إضافي، مثل FK EnrollmentId في CodeSubmissions. قيود UQ تنشئ فهارس فريدة أيضًا. المجموع 66 يشمل الجميع؛ لا نضيف فهرسًا مكررًا يبدأ بالأعمدة نفسها دون سبب. الفهارس تسرع بعض القراءات وتزيد تكلفة الكتابة والمساحة.

### Views وFunctions وStored Procedures

vAssessmentScores وvSubmissionOutcomes وvEnrollmentProgress استعلامات مسماة تحفظ المنطق، وليس نسخ بيانات يدوية. fnPercentage دالة Scalar تعيد قيمة؛ المقام صفر يعيد NULL. fnStudentCourseSummary دالة Inline Table-Valued تعيد جدولًا يمكن JOIN معه. uspEnrollStudent ينفذ عملية تسجيل متعددة الخطوات داخل معاملة؛ uspSubmitAssessment يعتمد على قيود اكتمال الإجابات؛ uspQueueCodeSubmission يثبت لقطة الكود. الإجراء يمكنه تنفيذ DML ومعاملات، بينما الدالة هنا للاستخدام داخل استعلام.

### Triggers والتحقق لعدة صفوف

Trigger ينفذ تلقائيًا مع DML. inserted وdeleted **جدولان** قد يحتويان عدة صفوف، لا صفًا واحدًا مضمونًا. Triggers الحالية تفحص EXISTS/JOIN لكل المجموعة؛ لذلك تحديث مفاتيح تصحيح عدة أسئلة أو إدخال ملفات طلاب بينها أدمن يفشل كاملًا. UPDLOCK,HOLDLOCK على الأب يمنعان سباق تعديل محتوى مع نشره أو إدخال إجابة مع إغلاق المحاولة؛ قد يحدث Deadlock فيُلغى طرف ويحتاج Backend إلى إعادة محاولة مدروسة.

### Transactions وTRY/CATCH

~~~sql
BEGIN TRY
 BEGIN TRANSACTION;
 -- عدة تغييرات يجب أن تنجح معًا
 COMMIT TRANSACTION;
END TRY
BEGIN CATCH
 IF XACT_STATE()<>0 ROLLBACK TRANSACTION;
 THROW;
END CATCH;
~~~

المعاملة تمنع نصف عملية ناجحة ونصفها فاشل. SET XACT_ABORT ON وTHROW يحافظان على الفشل الصريح. CREATE DATABASE خارج المعاملة الإلزامية للأجسام؛ لو فشل إنشاء الجداول تبقى قاعدة الاختبار الجديدة فارغة ولا نحذفها أو نعيد استخدام قاعدة موجودة تلقائيًا.

### ALTER وTRUNCATE وDROP

ALTER يغير تعريف جدول. TRUNCATE يزيل صفوف جدول كاملًا دون WHERE، وDROP يزيل الكائن نفسه. في ملف الأمثلة تُستخدم هذه الأوامر فقط على #LanguagePractice المؤقت داخل الجلسة. لا تُطبق على Users أو قاعدة CodeMentorAI_Learning. DELETE يسمح بشرط WHERE لكنه أيضًا ليس سياسة حذف مناسبة لتاريخ الإنجاز دون قرار احتفاظ.

## التطبيع وقواعد السلامة

1NF: كل هدف وخيار وتلميح ونتيجة حالة في صف مستقل. نص شرح طويل أو كود ليس قائمة علاقات يجب تفكيكها حرفًا حرفًا.

2NF: CodingTaskTopics يعتمد على TaskId وTopicId؛ لا نضع عنوان التمرين الذي يعتمد على TaskId وحده. نتائج الحالات تعتمد على التسليم والحالة معًا.

3NF منطقيًا: لا ننسخ اسم اللغة في كل كورس أو بريد الطالب في كل تسليم، ولا نخزن نسبة التقدم بوصفها حقيقة مستقلة. **استثناء فيزيائي مقصود:** AssessmentId في AttemptAnswers وTaskId في SubmissionTestResults زائدان قابلان للاشتقاق، لكنهما مقيدان بـFKs مركبة لمنع خلط الآباء بشكل تصريحي. لا نصف هذا التنفيذ بأنه خالٍ تمامًا من التكرار الفيزيائي؛ نذكر المقايضة بوضوح. التحقق عبر Triggers بدل هذه الأعمدة بديل ممكن، لكنه يحتاج ضبط تزامن إضافيًا.

FK وحده يثبت وجود الأب، لكنه لا يثبت أن Users.RoleCode=Student أو أن درسًا يتبع كورس التسجيل. دور الطالب يُفرض بـTriggers وFK إلى StudentProfiles، وملكية الكورس بالتحقق متعدد الجداول. ملكية طلب المستخدم المسجل ومصادقته تبقيان مسؤولية Backend موثوق.

| السؤال | الإجابة |
| --- | --- |
| PK مقابل FK؟ | PK يميز الصف، وFK يضمن أن مرجع الأب موجود؛ قد تكون الأعمدة نفسها PK وFK كما في StudentProfiles. |
| 1:1 في المشروع؟ | Users إلى StudentProfiles: حساب يملك صفرًا أو ملف طالب واحدًا بمفتاح مشترك. |
| 1:M؟ | Courses إلى Levels؛ كل مستوى يتبع كورسًا واحدًا والكورس يملك مستويات متعددة أو لا يملك أثناء المسودة. |
| M:N؟ | الطالب والكورس عبر Enrollments، والتمرين والموضوع عبر CodingTaskTopics. |
| لماذا EnrollmentId مع UQ؟ | لتسهيل الرجوع للتسجيل من أدلة متعددة، مع منع تكرار الطالب والكورس بالقيد الفريد. |
| INNER مقابل LEFT؟ | INNER يتطلب تطابقًا، LEFT يحتفظ بكل صف يسارًا مع NULL عند عدم التطابق. |
| RIGHT مقابل FULL؟ | RIGHT يحتفظ باليمين فقط كطرف مضمون، FULL يحتفظ بكل صف من الطرفين. |
| WHERE مقابل HAVING؟ | WHERE قبل GROUP BY، HAVING على مجموعات ناتجة. |
| لماذا GROUP BY؟ | لحساب ملخص لكل اختبار أو كورس بدل صف ملخص واحد للجميع. |
| هل Clustered يعني نتيجة مرتبة دائمًا؟ | لا؛ ترتيب العرض المضمون يحتاج ORDER BY. |
| View جدول مخزن؟ | في هذه القاعدة هو استعلام مسمى يحسب من الحقائق، وليس Snapshot مستقلًا. |
| Function مقابل Procedure؟ | Function هنا تنتج قيمة/جدولًا داخل SELECT؛ Procedure ينفذ عملية متعددة الخطوات مع DML ومعاملة. |
| متى Trigger؟ | لسلامة قاعدة يجب أن تصمد أمام DML مباشر أيضًا، مثل منع تعديل نسخة منشورة؛ لا يغني عن مصادقة Backend. |
| كيف نضمن عمل Trigger لعدة صفوف؟ | نتعامل مع inserted/deleted كمجموعات ونختبر إدخالًا وتحديثًا متعدد الصفوف فعليًا. |
| ما فائدة Subquery؟ | اختبار وجود علاقة أو المقارنة بقيمة مشتقة دون نسخها إلى جدول جديد. |
| لماذا ROLLBACK لا يعيد أرقام IDENTITY؟ | تخصيص الأرقام لا يتراجع؛ الفجوات طبيعية ولا تثبت حذف بيانات. |
| هل Completed يعني نجاح الحل؟ | يعني اكتمال التنفيذ المسموح؛ AllTestsPassed يتطلب نجاح كل الحالات المعرفة. |
| ماذا عن حالة لم تُنفذ؟ | ليست فاشلة؛ NotRun مشتق من عدد الحالات المعرفة ناقص النتائج الفعلية. |
| كيف نحافظ على نتيجة قديمة؟ | تجميد النسخة المنشورة والأسئلة والاختيارات والاختبارات، وإصدار IDs/VersionNo جديدة للتغيير. |
| هل بيانات المتصفح موثوقة؟ | لا؛ browser-import يحفظ المصدر والشك، ولا يحول درجة بلا إجابات إلى محاولة مخترعة. |
| هل عدد الجداول هدف؟ | لا؛ 23 نتيجة النطاق المعتمد والعلاقات المطلوبة، والحزم الاختيارية ليست جزءًا من التنفيذ. |

## Data Science وAI: المنفذ والمستقبلي

المنفذ يحفظ بنية تسمح بمحاولات متتابعة وإجابات ونسخ محتوى ونتائج كود ومصدر دليل. هذا مفيد للتحليل قبل ML. التوصيات الحالية قواعد ثابتة، والمحادثة الحالية مجهزة، ولا توجد أعمار حقيقية معتمدة أو زمن قراءة نشط أو حضور مؤكد أو تقييم شركات أو نماذج مدربة.

للتنبؤ مستقبلًا نحدد هدفًا وزمنًا، مثل اجتياز المستوى القادم خلال 14 يومًا باستخدام أدلة قبل AsOf فقط. نحتاج بيانات متعلمين حقيقيين كافية، وتقسيمًا حسب الطالب والزمن، ومنع تسرب النتيجة المستقبلية للمدخلات، ومقارنة بخط أساس ومعايرة ومراجعة الانحياز. لا ندرّب على ثلاث شخصيات خيالية أو نخلط مشاهدة الحل المرجعي مع إتقان مستقل.

حفظ محادثات المرشد والخدمات والإرشاد النظير والتدريب الافتراضي والمحافظ والشهادات وإصدارات النماذج والتوقعات حزم مستقبلية منفصلة. لم يُنشأ أي جدول لها في هذه المرحلة. الشهادة القابلة للتحقق تحتاج سياسة إصدار ودليلًا موثوقًا، وليس طباعة صفحة فحسب.
